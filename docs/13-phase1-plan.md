## 13.1 Python 워커가 사라집니다

[03 §3](03-architecture.md)에서 이미지 처리 워커를 Python + OpenCV로 분리했습니다.
**이유는 원근 보정·마커 정합·crop이었고, 그게 전부 없어졌습니다.**

지금 파이프라인에 이미지 연산이라고 할 만한 것은 두 가지뿐입니다.

| 하는 일 | 필요한 것 |
|---|---|
| 사진 크기를 2576px로 줄여 API에 보냄 | 아무 이미지 라이브러리 |
| (선택) 머리말 마스킹 | 사각형 하나 칠하기 |

**OpenCV도, 별도 서비스도, 다른 언어도 필요 없습니다.**
나머지는 전부 API 호출과 규칙 판정이라 TypeScript 한 곳에서 끝납니다.

| 영역 | 선택 | 바뀐 점 |
|---|---|---|
| 웹 + API | Next.js (App Router) + TypeScript + Tailwind | 유지 |
| ~~이미지 워커~~ | ~~Python + OpenCV~~ | 🛑 **삭제** |
| 백그라운드 처리 | Next.js Route Handler + Postgres `jobs` | 유지 (언어만 통일) |
| DB / 스토리지 / 인증 | Supabase | 유지 |
| AI 채점 | Claude API (`@anthropic-ai/sdk`) | 유지 |
| ~~pdf.js~~ | | 🛑 **삭제** — 템플릿 편집기가 없어졌으므로 |
| 배포 | Vercel + Supabase | 워커 호스팅 불필요 |

**서비스 하나, 언어 하나, 배포 대상 하나.** `tools/`의 파이썬은 실험 도구로 남고
제품에는 들어가지 않습니다 — 프롬프트와 스키마만 TypeScript로 옮깁니다.

### Vercel Pro · Supabase Pro 기준 (2026-08-07 확인)

| 조건 | 설계에 미치는 영향 |
|---|---|
| Vercel Pro — 함수 최대 300초 | **한 장에 20~40초라 장당 호출은 여유. 배치를 한 요청에 담는 건 불가** |
| Supabase Pro — 무활동 중지 없음 | 방학처럼 뜸한 기간에도 첫 요청이 안 죽음 |
| Supabase Pro — 저장소 100GB | 사진 보관 정책이 필요 (§13.7) |

첫 줄이 큐 설계를 정합니다. **30장을 한 요청에서 처리하면 300초를 넘겨 죽습니다.**
장 하나에 호출 하나로 쪼개야 하고, 그러면 40초짜리라 넉넉합니다.

## 13.2 무엇을 만들지 — 조교의 하루로 정의합니다

지금 조교가 하는 일:

```
시험지 걷음 → 선생님이 채점 → 오답 정리 → 재시험 명단 만듦 → 학생에게 통보
```

Phase 1이 바꾸는 것:

```
시험지 걷음 → 사진 찍어 올림 → (자동 채점) → 선생님이 화면에서 확인·수정 → 확정
                                                  ↓
                                   재시험 명단 · 오답 목록이 그대로 나옴
```

**"선생님이 채점한다"가 "선생님이 확인한다"로 바뀌는 것**이 전부입니다.
초기에는 전 장을 확인하므로 자동 확정이 없습니다. 그래도 백지에서 채점하는 것보다
훨씬 빠르고, **그 확인 기록이 곧 정확도 데이터**가 됩니다([12 §12.8](12-page-level-grading.md)).

## 13.3 마일스톤 — 각 단계가 그 자체로 쓸모 있어야 합니다

### M1 · 한 반의 한 시험을 끝까지 (최우선)

> 🛑 **"한 반의 한 시험"이라는 묶음은 §13.9에서 없어졌습니다.**
> 학생마다 보는 시험이 달라서, 단위는 반이 아니라 **답안지 한 벌**입니다.
> 아래 항목들은 그대로 유효하고 묶는 방식만 바뀌었습니다.

**이것만으로 실제 수업에서 써볼 수 있어야 합니다.**

```
✅ 사진 여러 장 업로드 (모바일 웹, 카메라 직접 촬영 포함)
✅ 자동 채점 — 전사 → 판정 → PASS/FAIL
✅ 진행 표시 (30장이면 2~3분)
✅ 검수 화면 — 문항별 결과를 보고 고치고 확정
✅ 결과 화면 — PASS/FAIL 명단, 학생별 오답 목록
✅ 결과 내보내기 (복사·인쇄)
```

**의도적으로 안 넣는 것**

| 안 넣음 | 왜 |
|---|---|
| 반·학생 명단 등록 | **학생 이름을 머리말에서 읽습니다.** 명단 없이도 결과가 나옵니다 |
| 계정·권한 | 처음엔 한 계정으로. 여러 명 동시 사용은 M2 |
| 시험지 등록 | 없앤 것이 이 설계의 핵심입니다 |
| 자동 확정 | 1~2주차는 전 장 검수 |
| 정확도 대시보드 | 검수 기록만 쌓아두고 화면은 M3 |

명단 등록을 뺀 것이 중요합니다. **학원 명단 데이터를 기다리지 않고 시작할 수 있고**,
읽어낸 이름이 얼마나 정확한지도 M1에서 저절로 확인됩니다.

### M2 · 여러 명이 동시에 쓰기

```
✅ 교사·조교 계정 (Supabase Auth)
✅ 반·학생 명단 — 읽어낸 이름을 명단에 붙여 학생 ID로 정규화
✅ 시험 이력 — 같은 학생의 지난 결과를 봄
✅ 이름은 저장하지 않고 학생 ID로 치환 ([12 §12.9](12-page-level-grading.md))
```

### M3 · 검수를 줄이기

```
✅ 확신도 · 경계선(커트라인 ±2) · 밀림 경보 기반 라우팅
✅ 정확도 대시보드 — 선생님이 고친 것과 그대로 둔 것을 누적 집계
✅ 채점 규칙 설정 — 철자 엄격/관대를 시험 단위로
✅ 흔들리는 칸 검출 (같은 사진 2회 읽어 불일치 시 검수)
```

**M3의 근거는 M1·M2가 쌓은 데이터입니다.** 순서를 바꿀 수 없습니다.

### M4 · 이후

오답노트 자동 생성, 재시험지 생성, 학부모 리포트, 통계.

## 13.4 큐 — M1은 브라우저가 몰아줍니다

> 🛑 아래 그림의 `jobs` 표와 "업로드 → 30개 생성"은 §13.9에서 바뀌었습니다.
> 일감의 단위는 `sheets`의 한 행이고, 30개를 한꺼번에 만들지 않고
> **접수할 때마다 하나씩** 생깁니다. 브라우저가 몬다는 뼈대는 그대로입니다.

장당 호출로 쪼개야 하므로 누군가 여러 번 불러야 합니다.
**M1에서는 브라우저가 그 역할을 합니다.**

```
업로드 → job 행 30개 생성 → 즉시 응답
   ↓
브라우저가 /api/grade?job=N 을 동시 4개씩 호출
   ↓
끝난 것부터 화면에 채워짐 (진행률이 저절로 나옴)
```

크론도, 별도 워커도, 상태 머신도 필요 없습니다. **브라우저를 닫아도 job 행은
남아 있으므로** 다시 열면 이어서 처리합니다.

나중에 필요해지면(조교가 올려두고 나가는 흐름) Vercel Cron으로 미처리 job을
쓸어담는 것을 M2에 붙입니다. **지금 넣으면 쓰지도 않을 것을 디버깅하게 됩니다.**

## 13.4b M1에서 먼저 정해야 할 것

### 🔴 채점 규칙 — 철자를 엄격히 볼 것인가

선생님들은 지금 한 글자 오타를 **정답 처리합니다**
([12 §12.6](12-page-level-grading.md), 다섯 건 확인).

| 선택 | 결과 |
|---|---|
| 관대 (현재 기본) | 선생님과 잘 맞음. 대신 철자 오류가 그대로 통과 |
| 엄격 | 선생님보다 정확할 수 있음. 대신 '우리만 오답'이 늘어 초기 검수가 늘어남 |

**시스템이 정할 수 없는 교육 방침입니다.** M1은 관대를 기본값으로 두되
**조교 화면에서 바꿀 수 있게** 만들고, 실제 운영에서 정합니다.
(시험 단위로 두려 했으나 §13.9에서 시험 묶음 자체가 없어졌습니다.)

### 학생 이름 처리

머리말에서 읽되 **DB에는 학생 ID로만 저장**합니다. M1은 명단이 없으므로
이름을 임시로 들고 있다가, M2에서 명단이 붙으면 치환하고 버립니다.

## 13.8 현장 테스트에서 나온 것 (2026-08-07, 1단계)

배포 직후 실제 시험지 한 장으로 눌러봤습니다. **제한이라고 여긴 두 가지가
가장 값진 결과였습니다.**

### 🔴 양면 인쇄 시험지 — 설계에 없던 것

이 학원 시험지 중 **양면 인쇄된 것**이 있습니다. 앞면만 찍으면 60문항 중
47문항만 채점됩니다. 그리고 그대로 두면 이렇게 됩니다.

```
인쇄 60문항 · 촬영 47문항 · 그중 오답 3개 · 커트라인 -8
→ verdict(3, 8) = PASS
   안 찍힌 뒷면 13문항을 통째로 틀린 학생도 집에 갑니다.
```

**이건 버그였습니다.** 마침 커트라인이 빨간펜에 가려 판정이 안 나와서 드러나지
않았을 뿐입니다. 고친 것:

| 고침 | 내용 |
|---|---|
| 경보 등급 분리 | `drift`(밀림) / **`incomplete`(일부만 찍힘)** / `info`(구조 안내) |
| 판정 차단 | `incomplete`면 **PASS/FAIL을 내지 않습니다** |
| 문구 | "밀렸거나 빠졌습니다" → "60문항인데 47문항만 찍혔습니다(47번까지). **뒷면을 마저 찍어 함께 올리십시오**" |
| 여러 장 병합 | 한 학생의 여러 장을 **문항 번호로 정렬해 합칩니다.** 순서를 사람이 맞출 필요가 없습니다 |

원인이 다르면 조교가 할 일도 다릅니다. 밀림은 다시 찍어야 하고, 페이지 누락은
**한 장 더** 찍으면 됩니다. 같은 문구로 뭉뚱그리면 안 됩니다.

### 커트라인이 가려질 수 있다

채점 표시가 머리말을 덮어 커트라인을 못 읽었습니다. 판정을 안 낸 것은 맞는
동작이지만, 그러면 조교가 막힙니다.

→ **커트라인 직접 입력**을 폴백으로 넣었습니다. 다만 **시험 하나에 한 번**입니다 —
한 반 학생이 전부 같은 커트라인을 쓰므로 장마다 넣는 일이 아닙니다.
"조교 입력 0"이라는 원칙을 깨지 않는 선입니다.

### 2차 — 문법백지TEST 2장 (같은 날)

| | |
|---|---|
| 2쪽 · 빈칸 48칸 | 89초 · **$0.299** |
| 시스템이 읽은 칸 | 46 (2칸 못 읽음) |
| **틀린 문항** | **실제와 정확히 일치** |
| 커트라인 -6, 오답 3 | **PASS — 실제와 동일** |

**여기서 판정 차단이 과하다는 게 드러났습니다.** 2칸을 못 읽었다고 PASS/FAIL을
막았는데, 따져보면 막을 이유가 없었습니다.

```
못 읽은 2칸이 전부 오답이었다 쳐도 → 오답 5개 ≤ 허용 6개 → 여전히 PASS
```

**결정이 안 바뀝니다.** 반면 1차(60칸 중 47칸)는 다릅니다.

```
못 읽은 13칸이 전부 오답이었다 쳐도 → 오답 16개 > 허용 8개 → FAIL로 뒤집힘
```

→ 규칙을 바꿨습니다. **"덜 읽혔으면 막는다"가 아니라 "못 읽은 칸이 전부 틀렸다고
가정해도 결정이 바뀌면 막는다"**입니다. [12.8](12-page-level-grading.md)의 경계선
검수와 같은 발상입니다 — 불확실성이 결정을 뒤집을 수 있을 때만 사람을 부릅니다.

경보 문구도 고쳤습니다. **2장을 다 올렸는데 "뒷면을 마저 올리십시오"는 틀린 안내**입니다.

> ~~뒷면이나 다음 장을 마저 찍어 함께 올리십시오~~
> **2장을 올렸는데 48문항 중 46문항만 읽혔습니다 (46번까지, 2칸 부족).
> 장이 더 있는지 확인하시고, 다 올리셨다면 2칸을 놓친 것이니 검수해 주십시오.**

커트라인 비율(`-10%`)도 **인쇄된 전체 문항 기준**으로 세도록 고쳤습니다.
읽힌 칸만으로 세면 덜 읽힐수록 커트라인이 낮아져 통과가 쉬워집니다.

### 🔴 사진이 90도 누워 있었습니다 — 2칸 누락의 유력한 원인

올린 사진 두 장 다 **답안지가 가로로 누워** 있었습니다. 글자가 세로로 서 있고
종이가 옆으로 돌아간 상태입니다. [08](08-sample-analysis.md)에서 위험으로 잡아둔
"90도 회전 촬영"이 실사용에서 그대로 나왔습니다.

**그런데도 48칸 중 46칸을 읽고 오답을 정확히 맞혔습니다.**
회전은 **막는 요인이 아니라 깎아먹는 요인**입니다. 못 읽은 2칸이 그 대가일
가능성이 큽니다.

→ 사진마다 **↺ ↻ 돌리기 버튼**을 넣고, 가로로 누운 사진에는 테두리를 노랗게
칠하고 경고를 띄웁니다. **자동으로 돌리지는 않습니다** — 진짜 가로 시험지가
있을 수 있어 사람이 보고 정합니다.

### 이 시험지에서는 번호 검증이 힘을 못 씁니다

문법백지TEST의 빈칸에는 **번호가 인쇄돼 있지 않습니다.** 모델이 번호를 스스로
붙이므로 46칸을 읽으면 언제나 `1..46`으로 연속입니다.
→ **번호 연속성 검사가 무력합니다.**

2칸 부족이 잡힌 것은 오직 머리말의 `점 수 [ /48 ]` 덕분이었습니다.
이 유형에서는 **`printedTotal`이 유일한 검증 수단**입니다. 머리말이 가려지거나
없는 시험지라면 2칸이 빠진 것을 **아무도 모릅니다.**

| 시험지 유형 | 번호 연속성 | 첫 글자 | 언어 | 총 문항 수 |
|---|:--:|:--:|:--:|:--:|
| 단어시험 (번호 인쇄) | ✅ | ✅ | ✅ | ✅ |
| **문법 빈칸 (번호 없음)** | ❌ | ❌ | 🟡 | ✅ **유일** |

### 머리말 병합이 맞게 동작했습니다

2쪽 머리말은 학생명·점수·커트라인이 **전부 공란**이었습니다.
병합이 1쪽 값을 가져왔고, 문항 수는 큰 값(48)을 취했습니다. 설계대로입니다.

### 🟢 문법백지TEST 유형 판단을 정정합니다

[12 §12.12](12-page-level-grading.md)에서 문법 시험지를 대상 밖 후보로 뒀는데,
**빈칸 채우기형은 잘 됩니다.** 48칸 중 46칸을 읽고 틀린 문항이 정확히 일치했습니다.

Phase 0에서 걸렸던 것은 **자유 나열형**(`1) 동명사만 쓰는 동사: enjoy, finish…`)
한 부분이었습니다. 그건 여전히 대상 밖이지만, **문법 시험지 전체가 아닙니다.**

| 유형 | 판단 |
|---|---|
| 단어시험 (표·밑줄·첫글자) | ✅ 대상 |
| **문법 빈칸 채우기** | ✅ **대상** ← 이번에 확인 |
| 자유 나열형 | ❌ 대상 밖 — 붙일 앵커가 없음 |
| 서술형·직독직해 | ❌ 대상 밖 |

### 3차 — 단어시험 2장 (같은 날)

| | |
|---|---|
| 2쪽 · 50문항 · 커트라인 -7 | 79초 · **$0.274** |
| 전 문항 인지 | ✅ 부족분 없음 |
| 사람 채점 | 오답 **5개** |
| 시스템 채점 | 오답 **7개** (사람이 놓친 2개를 더 잡음) |
| 결과 | **PASS** (7 ≤ 7) |

### 비용과 시간이 두 번 측정으로 수렴합니다

| | 쪽 | 문항 | 시간 | 비용 | 쪽당 |
|---|--:|--:|--:|--:|--:|
| 2차 문법백지 | 2 | 48 | 89초 | $0.299 | $0.150 |
| 3차 단어시험 | 2 | 50 | 79초 | $0.274 | $0.137 |

**쪽당 $0.14 · 40초**로 보면 됩니다. Phase 0의 실측 추정($0.118/장)보다 조금
비싼데, 판정 호출이 한 번 더 붙기 때문입니다.

| 규모 | 비용 | 시간(학생 4명씩 동시 처리) |
|---|--:|--:|
| 한 반 20명 · 2쪽 | **$5.6** (약 8천 원) | 약 6분 30초 |
| 하루 300쪽 | **$42** | — |

**한 반에 8천 원**입니다. 선생님이 한 반 채점에 쓰는 시간을 생각하면 문제가
되는 금액이 아닙니다. 다만 **하루 300쪽을 매일 돌리면 월 120만 원 선**이라
M2에서 Sonnet 5 전환을 검토할 근거는 됩니다 — 검수 화면이 생겨 회귀를
귀속시킬 수 있게 된 뒤입니다.

이 숫자가 **큐 설계를 정합니다.** 한 반이 6분 넘게 걸리므로 조교가 브라우저를
띄워놓고 기다릴 수는 있지만 **탭을 닫으면 안 되는 구조는 못 씁니다.**
진행 상황이 서버에 남아야 합니다 (§13.9).

### 🔴 이 답안지가 정확히 경계선이었는데 화면이 아무 말도 안 했습니다

```
사람 기준   오답 5 / 허용 7 → PASS (여유 2)
시스템 기준 오답 7 / 허용 7 → PASS (여유 0)   ← 한 문항만 더면 FAIL
```

`compare()`가 `nearBoundary`를 계산은 하고 있었지만 **API 응답에도, 화면에도
내보내지 않고 있었습니다.** [12.8](12-page-level-grading.md)에서 "경계선 검수"를
Phase 1의 핵심 안전장치로 잡아놓고 정작 가장 필요한 장에서 침묵한 것입니다.

→ 응답에 `nearBoundary`·`margin`을 싣고, 화면에 눈에 띄게 띄웁니다.

> 🔶 **커트라인에 걸렸습니다 — 반드시 확인하십시오.**
> 오답 7개 / 허용 7개 — 여유가 없습니다. 한 문항만 더 틀렸으면 결과가 뒤집힙니다.

### 🟢 시스템이 사람보다 정확했습니다 — 그런데 그게 위험도 만듭니다

선생님이 놓친 오답 2개를 잡아냈습니다. [12.8](12-page-level-grading.md)에
적어둔 경고가 실제로 확인된 셈입니다 — **선생님 채점은 완전한 정답 라벨이
아닙니다.** 벤치마크에서 이런 건은 "우리만 오답"으로 집계돼 마치 우리가
틀린 것처럼 보이지만, 사실은 우리가 맞은 것입니다.

**동시에 이게 운영 리스크입니다.** 시스템이 습관적으로 선생님보다 2개를 더
잡는다면, **커트라인 근처 학생들이 사람 채점 때보다 더 자주 탈락합니다.**
이번 답안지가 정확히 그 경계에 있었습니다 — 사람은 여유 2개, 시스템은 여유 0개.

이건 버그가 아니라 **방침 문제**입니다.

| 선택 | 결과 |
|---|---|
| 시스템 기준대로 | 더 정확하지만 재시험이 늘어남. 학부모 문의도 늘어날 수 있음 |
| 선생님 관행에 맞춤 | 마찰이 적지만 틀린 답이 통과함 |
| **경계선만 사람이 확정** | 대부분 자동, 갈리는 지점만 선생님이 결정 ← 지금 설계 |

세 번째가 지금 설계이고, 이번 사례가 그 필요를 실증했습니다.
**"더 정확한 것"이 곧 "그대로 써도 되는 것"은 아닙니다.**

### 잘 된 것

- 학생이 쓴 것을 **매우 높은 확률로 바르게 전사**
- 촬영된 범위 안에서 **오답 수 판독이 정확히 일치**
- **밀림 없음**
- 이미 빨간펜으로 채점된 시험지였는데도 전사가 견뎠습니다 —
  [08](08-sample-analysis.md)에서 걱정하던 것보다 나았습니다

## 13.7 사진 보관 — 90일

실제 업로드 샘플 14장의 평균이 **1.53MB**(0.55~2.73)였습니다. 하루 300장이면:

| 무엇을 저장하나 | 월 증가 | 90일 보관 시 정상 상태 |
|---|---:|---:|
| 휴대폰 원본 그대로 | 9.9GB | 29.7GB |
| **API에 보낸 축소본(2576px)** | **2.6GB** | **7.7GB** |

**축소본을 저장합니다.** 용량 때문만이 아니라 **그게 감사에 맞는 물건**이기 때문입니다.
나중에 "왜 이렇게 채점했나"를 되짚을 때 봐야 할 것은 휴대폰 원본이 아니라
**모델이 실제로 본 이미지**입니다.

보관 기간은 **90일**로 둡니다. 재시험·이의 제기 주기를 덮으면서, 학생 답안
사진을 무기한 쌓아두지 않습니다. 채점 결과(전사·판정·검수 기록)는 이미지와 분리해
계속 보관합니다 — 개인정보 부담이 훨씬 작고 정확도 추적에 필요합니다.

> 저장소 걱정이 없어도 **개인정보는 안 쌓는 게 원칙**입니다.
> 유출 사고가 나도 잃을 게 없는 상태를 유지합니다.

## 13.9 🔴 접수 단위로 다시 짰습니다 (2026-08-08)

**설계를 하나 잘못 깔았습니다.** "한 반이 같은 시험을 본다"고 놓고
`exams` 표를 만들었는데, 원장님 지적으로 뒤집혔습니다.

> 보통 보는 시험이 학생별로도 다 달라서 굳이 한 반을 다 채점하는 방식으로
> 할 필요는 없어.

같은 반이라도 학생마다 진도가 달라 **보는 시험이 다릅니다.** 그러면
`exams`는 묶을 것이 없는 빈 껍데기이고, 시험을 만들라고 요구하는 화면은
**조교에게 없어도 될 일을 시키는 것**입니다.

### 실제 흐름

```
조교A: 학생1 접수 → 즉시 채점 시작
              ↓ (채점 도는 중)
       학생2 접수 → 이것도 즉시 채점 시작
조교B: 학생3 접수 → 마찬가지. 조교A와 무관하게

한 학생의 시험지가 두 조교에게 동시에 접수될 일은 없음
```

**"모아서 돌린다"가 아니라 "받는 대로 흘려보낸다"입니다.**
조교는 화면을 하루 종일 열어두고 학생이 낼 때마다 찍습니다.

### 무엇이 없어졌나

| 없앤 것 | 왜 |
|---|---|
| `exams` 표 | 묶을 것이 없음. 시험 이름은 머리말에서 읽어 답안지 행에 둠 |
| 시험 만들기 화면 | 조교가 채울 항목이 하나 더 있는 것뿐 |
| 사진을 학생별로 자르는 UI | 애초에 한 번에 한 학생분만 찍음 |
| `claim_sheets(exam, n)` | 시험 단위로 집을 이유가 사라짐 |

### 무엇이 남았나

시험 단위로 두려던 **커트라인·철자 방침**은 갈 곳이 달라졌습니다.

| 항목 | 어디로 |
|---|---|
| 커트라인 | **시험지에서 읽습니다.** 못 읽었을 때만 그 답안지에 직접 넣습니다 |
| 철자 엄격/관대 | 조교 화면에 남는 값. 한 번 정하면 다음 학생에도 그대로 |
| 반 | 선택 사항. 적어두면 명단이 반별로 묶입니다 |

**커트라인을 미리 받지 않는 것이 중요합니다.** 학생마다 시험이 다른데
앞 학생의 커트라인이 다음 학생에게 조용히 붙으면 판정이 틀립니다.

### 커트라인은 다시 채점하지 않고 고칩니다

1차 현장 테스트에서 빨간펜이 머리말을 덮어 커트라인을 못 읽었습니다.
그때 모자란 것은 **숫자 하나**뿐인데 다시 채점하면 $0.14가 또 나갑니다.

→ 전사도 판정도 이미 저장돼 있으므로 `/api/sheets/{id}/cutline`이
**모델을 안 부르고 셈만 다시 합니다.** 답안지 줄에 입력칸이 그 자리에 뜹니다.

### 큐 — 집는 방법이 둘

```
claim_sheet(id)   방금 접수한 그 장을 집는다      ← 접수 직후
claim_next(n)     떠도는 것을 아무거나 집는다      ← 화면을 연 사람이 쓸어담음
```

뒤쪽이 있어야 **조교가 채점 도중 창을 닫아도 그 한 장이 버려지지 않습니다.**
조교B의 브라우저가 조교A가 놓고 간 것을 주워 마저 채점합니다 — 채점은
누가 돌리든 결과가 같으므로 나눌 이유가 없습니다.

둘 다 `for update skip locked`라 동시에 눌러도 겹치지 않습니다.
브라우저 하나가 동시에 도는 갈래는 넷까지입니다.

### 화면

| 경로 | 무엇 |
|---|---|
| `/` | **접수** — 사진 찍어 접수, 그날 접수 목록이 실시간으로 갱신 |
| `/quick` | 저장 없이 한 명분만 눌러보는 자리 |

목록 위에 나오는 숫자 중 중요한 것은 "몇 명 끝났나"가 아닙니다.

> 🔶 **N명은 사람이 반드시 봐야 합니다** — 커트라인·밀림·판정 보류

### 데이터 구조에서 유지된 것

시험 표만 빠졌고 나머지 판단은 그대로입니다.

- **큐 테이블을 따로 두지 않습니다.** 일감의 단위가 답안지 한 벌이고
  그게 곧 `sheets`의 한 행입니다. 두 곳에 적으면 언젠가 어긋납니다.
- **문항은 표로 둡니다.** `items.teacher_correct`(선생님이 뒤집은 것만),
  `final_correct`(화면이 보는 값), `overturned`(정확도 측정) — 뒤의 둘은
  DB가 계산합니다.
- **RLS는 "직원인가"까지만.** 역할로 갈리는 것은 확정 하나이고 트리거가 막습니다.
- **사진은 축소본만 90일.** 지운 뒤에도 행은 남깁니다.

### 다음 — 3단계 검수 화면

지금은 답안지 한 줄에 오답 수와 PASS/FAIL만 나옵니다. 문항을 열어 고치고
확정하는 것이 3단계이고, 그 고친 기록이 `items.teacher_correct`에 쌓여
정확도 데이터가 됩니다.

## 13.10 3단계 — 검수 화면 (2026-08-08)

접수 목록에서 답안지를 누르면 `/sheets/{id}`가 열립니다.
[13.2](#132-무엇을-만들지--조교의-하루로-정의합니다)의 **"선생님이 채점한다 →
선생님이 확인한다"가 실제로 일어나는 화면**입니다.

### 무엇을 보여주나

| | 왜 |
|---|---|
| 모델이 본 사진 (서명 URL) | **전사가 종이와 같은지**는 사진을 봐야 압니다 |
| 문항별 제시어·학생이 쓴 것·정답·판정·비고 | 채점의 근거 전부 |
| 경계선·밀림·일부만 찍힘 경보 | 여기가 사람을 부른 이유 |
| 커트라인 입력칸 (못 읽었을 때) | 다시 채점하지 않고 셈만 고침 |

### 고치면 그 자리에서 다시 셉니다

문항의 ○/✗를 누르면 `items.teacher_correct`에 들어가고, 곧바로
`/api/sheets/{id}/recount`가 **모델 없이** 오답 수와 PASS/FAIL을 다시 셉니다.

```
선생님이 1번을 정답 처리 → 오답 7 → 6 → 여유 0 → -1 → 경계선에서 벗어남
```

**셈은 서버가 합니다.** 화면이 따로 세면 언젠가 서버와 어긋나고,
그 어긋남이 학생의 PASS/FAIL입니다.

다시 채점(모델 재호출)을 하지 않는 이유는 비용($0.14)만이 아닙니다.
**새로 전사하면 선생님이 방금 검수한 내용이 덮입니다.**

### 시스템과 같은 값이라도 누르면 기록합니다

`teacher_correct`는 "선생님이 바꾼 것만" 채우는 칸으로 설계했지만,
**같은 값을 눌러도 채웁니다.**

```
teacher_correct is null      아무도 안 봤다
teacher_correct = correct    사람이 보고 그대로 뒀다   ← 이게 필요한 사실입니다
teacher_correct ≠ correct    사람이 뒤집었다 (overturned)
```

검수를 줄일지 판단하려면 **"봤는데 맞더라"가 몇 건인지**를 알아야 합니다.
안 본 것과 뭉뚱그리면 분모가 사라집니다.

### 확정은 선생님만, 취소도 있습니다

조교 화면에서는 확정 버튼이 안 보이고, 보이더라도 DB 트리거가 막습니다.
잘못 눌렀을 때 나갈 길로 **확정 취소**를 뒀습니다 —
취소하면 "누가 언제 확정했다"는 도장도 함께 지웁니다(0005).
남겨두면 확정되지 않은 답안지에 확정 기록이 붙어 나중에 잘못 읽힙니다.

### 다음 — 4단계 결과·명단 화면

`retest_roster`·`wrong_items` 뷰는 이미 있습니다. 남은 것은 화면과
내보내기(복사·인쇄)입니다.

## 13.11 4단계 — 결과·명단 화면 (2026-08-08)

`/roster`. 조교가 하던 **"오답 정리 → 재시험 명단 만들기"**가 이 화면입니다.

| 칸 | 무엇 |
|---|---|
| 재시험 | **확정된 FAIL만.** 반별로 묶임 |
| 통과 | 확정된 PASS |
| 오답 목록 | 확정된 답안지의 오답을 학생별로 |

각 칸에 **복사** 버튼, 화면 위에 **인쇄** 버튼이 있습니다.
인쇄하면 조작 요소는 빠지고 명단만 나갑니다.

### 확정 안 된 것을 어느 칸에도 넣지 않습니다

이게 이 화면의 유일한 어려운 판단입니다.

```
채점 중 · 검수 대기 · 실패  →  전부 "미확정"
```

통과로 세면 **재시험 갈 학생이 집에 갑니다.** 재시험으로 세면 **통과한
학생을 붙잡습니다.** 둘 다 안 되므로 세 번째 칸을 만들고, 남아 있으면
화면 맨 위에 띄웁니다.

> ⏳ **아직 확정되지 않은 답안지가 3장 있습니다. 지금 명단은 완성이 아닙니다.**

**복사한 글 안에도 같은 문구가 들어갑니다.** 화면 경고는 붙여넣기를 따라가지
않기 때문입니다 — 메신저에 붙인 명단만 보고 학생을 보내면 경고를 본 사람이
없습니다.

### 검수 전 판정으로 오답노트를 뿌리지 않습니다

`wrong_items` 뷰는 확정 여부를 안 봅니다(그래야 "덜 됐다"를 셀 수 있습니다).
거르는 것은 화면이 합니다 — 명단에 나가는 오답은 **확정된 답안지의 것뿐**입니다.

### 오답은 제시어 → 쓴 것 → 정답으로 적습니다

```
7. expectation → 관전 (정답: 관점)
12. refrigerator → (무응답) (정답: 냉장고)
```

무응답도 적습니다. 빈칸으로 두면 **왜 틀렸는지가 안 보입니다.**
이 형식 그대로 오답노트·재시험지의 재료가 됩니다(M4).

### M1이 끝났습니다

```
✅ 접수 — 사진 찍어 올리면 즉시 채점
✅ 큐 · 진행 표시 — 창을 닫아도 안 잃음
✅ 검수 화면 — 문항별로 고치고 확정
✅ 결과·명단 화면 — 재시험 명단 · 오답 목록 · 복사 · 인쇄
⬜ 실제 수업에서 한 반 돌려보기  ← 남은 것
```

마지막 항목은 코드가 아니라 **개인정보 동의서**가 막고 있습니다([13.5](#135-남은-위험)).

## 13.12 모델 비교 — 값싼 모델로 바꾸면 무엇을 잃는가 (2026-08-08)

`/bench` (관리자만). 하루 300쪽이면 월 120만 원이라 이건 실제 돈 문제입니다.

### 무엇을 재느냐가 답을 바꿉니다

문항 정답률로 재면 **"97%면 충분한가?"라는 답 없는 논쟁**이 됩니다.
이 시스템이 내놓는 것은 PASS/FAIL 하나이고 학생에게 일어나는 일도 그것뿐이므로,
첫 지표는 **판정이 갈리는가**입니다([12 §12.8](12-page-level-grading.md)).

```
판정 일치 96.0% (24/25장)   ← 결론
뒤집힘 1장                  ← 이게 있으면 못 바꿉니다
한쪽만 판정 2장             ← 값싼 모델이 커트라인을 못 읽은 것
```

나머지 숫자(전사 차이·놓친 칸·문항 정오)는 **갈린 이유를 짚기 위한** 것이지
그 자체가 합격선이 아닙니다.

### 한쪽만 판정한 장을 일치율에 넣지 않습니다

값싼 모델이 머리말을 못 읽어 커트라인이 없으면 판정이 안 나옵니다.
그걸 "불일치"로 세면 지나치게 나빠 보이고, **"일치"로 세면 일치율이 부풀려집니다.**
셋째 칸으로 뺍니다 — 명단 화면의 미확정과 같은 발상입니다(§13.11).

### 실제 결과를 건드리지 않습니다

`model_trials` 표에 따로 쌓습니다. `sheets`·`items`는 **학생에게 나간 결과**이고
여기는 "만약 다른 모델이었다면"입니다. 섞으면 실험 때문에 판정이 바뀝니다.

커트라인·철자 방침은 **실제 채점과 같은 규칙**을 씁니다. 조건을 바꿔놓고
비교하면 갈린 이유가 모델 차이인지 조건 차이인지 알 수 없습니다.

### 기준은 선생님이 고친 값이 아닙니다

`items.correct`(시스템이 내놓은 것)를 기준으로 씁니다. 여기서 답하려는 질문은
**"값싼 모델이 지금 나가는 결과를 재현하는가"**이고, 선생님 판정을 기준에 두면
모델 차이와 선생님의 수정이 뒤섞입니다.

### 실패도 결과로 남깁니다

값싼 모델이 스키마를 못 맞추거나 거절하면 그 사유를 `error`에 적어 화면에
띄웁니다. 지우면 **"돌려봤더니 잘 되더라"는 잘못된 인상**만 남습니다.

### 사고 강도도 '하위 단계'입니다

모델을 낮추는 것 말고 **같은 모델의 effort를 낮추는** 길도 있습니다.
Opus 5 + low가 Sonnet 5 + high보다 나을 수도 있고, 그건 돌려봐야 압니다.
그래서 모델과 사고 강도를 따로 고르게 두었습니다.

| 모델 | 입력/출력 (1M당) | Opus 대비 |
|---|---|---|
| Opus 5 (기준) | $5 / $25 | — |
| Sonnet 5 | $3 / $15 | 약 60% |
| Haiku 4.5 | $1 / $5 | 약 20% |

**25장을 돌리면 실험비가 $1 안팎**입니다. 월 120만 원을 걸고 판단하는 값으로는 쌉니다.

## 13.13 🔴 잡음 바닥을 먼저 재야 했습니다 (2026-08-08)

Sonnet 5를 재고 "뒤집힘 1장이니 못 쓴다"고 결론지었습니다.
그다음 **같은 모델(Opus 5 · high)로 같은 답안지를 다시 돌렸더니 똑같이
1장이 뒤집혔습니다.** 같은 장이었습니다.

```
박준희 · 48문항 · 커트라인 -4
  1차 Opus  오답 4 → PASS   (여유 0 · 🔶 경계선)
  2차 Opus  오답 5 → FAIL   ← 31번 하나가 갈렸을 뿐
```

**모델을 바꾸지 않았는데 판정이 뒤집혔습니다.**
이 장의 뒤집힘은 Sonnet의 흠이 아니었습니다. 잘못 귀속한 것입니다.

### 두 번 돌린 값이 잡음 바닥입니다

| | Opus vs Opus (잡음) | Sonnet vs Opus |
|---|--:|--:|
| 문항 정오 불일치 | **3** / 203 | **10** / 200 |
| 전사가 다른 칸 | **9** | **22** |
| 비용 | 103.7% | 70.4% |
| 시간 | 357초 | 364초 |

Sonnet의 차이는 잡음의 **2~3배**입니다. 여전히 나쁘지만
"뒤집힘 1장"이라는 사형선고와는 다른 이야기입니다.

**바닥을 안 재고 대상을 재면, 바닥이 대상의 탓으로 계산됩니다.**

### 경계선에서 갈린 것을 따로 셉니다

여유 0인 답안지는 **문항 하나만 흔들려도 뒤집힙니다.** 모델이 무엇이든
그렇습니다. 그래서 뒤집힘을 둘로 나눕니다.

```
뒤집힘 N장            ← 여유가 있었는데도 갈림. 이게 늘면 못 바꿉니다
경계선에서 갈림 N장    ← 원래 사람이 확정하는 자리. 모델 탓이 아닙니다
```

### 🟢 경계선 검수가 다시 한번 옳았습니다

[12 §12.8](12-page-level-grading.md)에서 커트라인 ±2를 사람에게 넘기기로
한 것은 "모델이 틀릴 수 있으니까"였습니다. 이번 실측은 더 강한 근거를 줍니다.

> **같은 모델이 같은 사진을 두 번 읽어도 그 자리에서는 답이 달라집니다.**

모델을 아무리 좋게 만들어도 없어지지 않는 성질입니다. 경계선 답안지를
사람이 확정하는 것은 임시 방편이 아니라 **영구적으로 옳은 설계**입니다.

### 사고 강도는 아직 안 재봤습니다

이번 2차는 `high`였으므로 **effort를 낮춘 결과가 아닙니다.**
`Opus 5 + low`는 여전히 미측정입니다.

### 앞으로 이 순서로 잽니다

```
1. Opus + high 를 한 번 더 돌려 잡음 바닥을 잡는다
2. 대상 조합을 돌린다
3. 대상의 차이에서 바닥을 빼고 본다
4. 뒤집힘은 '여유 있었는데도 갈린 것'만 센다
```

## 13.14 🔴 판정 일치율의 맹점 — 관대한 모델은 만점을 받습니다 (2026-08-08)

`Sonnet 5 + low`를 돌렸더니 **판정 일치 100%**가 나왔습니다.
비용 47%, 시간 53%. 숫자만 보면 바꿔야 합니다.

**바꾸면 안 됩니다.**

### 오답을 절반만 잡았습니다

| 학생 | Opus 오답 | Sonnet-low 오답 | 갈린 문항 |
|---|--:|--:|---|
| 기천용 | 2 | **0** | −44, −49 |
| 신균수 | 1 | **0** | −13 |
| (12칸) | 2 | **0** | −4, −8 |
| 신준상 | 3 | **2** | −24 |
| 박준희 | 4 | 4 | 없음 |

**정오가 갈린 7건 중 6건이 한 방향**입니다 — 전부 "Opus는 틀렸다는데
Sonnet-low는 맞다고 함". 잡음이면 위아래로 흩어져야 합니다.

### 왜 판정 일치율이 이걸 못 잡았나

**통과할 학생을 더 통과시켜도 판정은 그대로이기 때문입니다.**

```
오답 2 → PASS
오답 0 → PASS      판정 일치 ✅
```

극단적으로 **"전 문항 정답"이라고만 답하는 모델**도 이 표본에서는
판정 일치 100%가 나옵니다. 비교된 4장이 전부 PASS였기 때문입니다.

> 제가 이 벤치마크를 판정 일치율 하나로 설계했고, 그 지표가 여기서 뚫렸습니다.

### 고친 것

| 추가 | 무엇 |
|---|---|
| `itemsWrongOnlyBase` / `itemsWrongOnlyTrial` | 정오 불일치의 **방향** |
| `bias()` | 3건 이상이고 한쪽이 75% 이상이면 `lenient` / `strict` |
| `allComparedPass` | 비교된 장이 전부 PASS면 **표본에 판별력이 없다**고 경고 |

화면에 이렇게 뜹니다.

> 🔴 **대상이 오답을 놓치는 쪽으로 치우쳤습니다.** (놓친 오답 6 · 더 잡은 오답 1)
> **판정 일치율은 이걸 못 잡습니다** — 통과할 학생을 더 통과시켜도 판정은 그대로이기 때문입니다.
> 게다가 비교된 장이 전부 PASS라, 이 표본은 관대한 모델을 걸러낼 힘이 없습니다.

### 사고 강도가 채점 방침을 바꿉니다

같은 Sonnet 5인데 강도만 다릅니다.

| | 오답 총계(비교 가능 장) | 방향 |
|---|--:|---|
| Opus 5 · high (기준) | 11 | — |
| Sonnet 5 · **high** | 16 | 엄격 |
| Sonnet 5 · **low** | 6 | **관대** |

**`effort`는 비용 손잡이가 아니라 채점 방침 손잡이입니다.**
낮추면 판정 단계가 덜 따지고 "비슷하면 정답"으로 기웁니다.
전사 차이는 22 → 23으로 그대로였습니다 — **읽기는 안 변하고 판정만 변했습니다.**
[12 §12.7](12-page-level-grading.md)의 실측(전사 단계는 사고를 안 쓴다)과 맞습니다.

### 지금까지의 정리

| 조합 | 판정 | 전사 차이 | 정오 방향 | 비용 | 시간 | 판단 |
|---|---|--:|---|--:|--:|---|
| Opus · high (재실행) | — | 9 | 균형 | 104% | 104% | **잡음 바닥** |
| Sonnet · high | 경계선 1 | 22 | 엄격 | 70% | 106% | ❌ |
| Sonnet · low | 일치 | 23 | **관대** | 47% | 53% | ❌ |

**Sonnet은 어느 강도에서도 읽기가 2.5배 흔들립니다**(9 → 22~23).
강도는 그 위에서 채점을 엄격/관대로 흔들 뿐입니다.

### 다음에 재볼 것

`Opus 5 + low`는 여전히 미측정입니다. 이번 결과로 예측이 생겼습니다.

> 전사 차이는 잡음 바닥(9)에 가깝고, 정오는 관대 쪽으로 쏠릴 것이다.

맞으면 **"읽기는 Opus, 판정은 강도 높게"** 가 유일하게 안전한 조합이라는
뜻이고, 그건 지금 쓰는 설정입니다. 절감할 곳이 없다는 결론이 됩니다.
틀리면 그때 다시 봅니다.

**표본도 바꿔야 합니다.** 지금 4장이 전부 PASS라 판별력이 없습니다.
**FAIL이 섞인 날**로 돌려야 관대한 모델이 걸립니다.

## 13.15 🟢 `Opus 5 + low` — 잡음 안에 들어옵니다 (2026-08-08)

| | 잡음 바닥<br>(Opus·high 재실행) | **Opus · low** | Sonnet · high | Sonnet · low |
|---|--:|--:|--:|--:|
| 여유 있는데 뒤집힘 | 0 | **0** | 0 | 0 |
| 문항 정오 불일치 | 3 / 203 | **2 / 214** | 10 / 200 | 7 / 200 |
| 전사가 다른 칸 | 9 | **10** | 22 | 23 |
| 놓친 칸 | 14 | **3** | 17 | 17 |
| 정오 방향 | 균형 | 균형(2건) | 엄격 | **관대** |
| 비용 | 104% | **82%** | 70% | 47% |
| 시간 | 104% | **74%** | 106% | 53% |

**`Opus·low`가 `Opus·high`와 다른 정도가, `Opus·high`가 자기 자신과 다른 정도보다
작습니다.** 잡음과 구별이 안 된다는 뜻이고, 이보다 나은 결과는 나올 수 없습니다.

### 예측은 반만 맞았습니다

> 전사 차이는 잡음 바닥(9) 근처, 정오는 **관대 쪽으로 쏠릴 것**

전사는 맞았습니다(10). **정오는 틀렸습니다** — 불일치가 2건뿐이고 둘 다
`+`(대상이 더 잡음)였습니다. `bias()`가 3건 미만이라 방향을 말하지 않았고,
그게 맞는 처리입니다.

Sonnet이 `low`에서 관대해진 것은 **강도 탓이 아니라 모델 탓**이었습니다.
Opus는 덜 따져도 판정이 흔들리지 않습니다.

### 강도는 판정 단계만 건드립니다

전사 차이가 세 조합 내내 그 모델의 값 그대로입니다.

```
Opus   high 9 → low 10     (모델이 같으면 강도를 바꿔도 읽기는 그대로)
Sonnet high 22 → low 23
```

[12 §12.7](12-page-level-grading.md)의 실측(전사 단계는 사고를 안 쓴다)이
세 번 더 확인됐습니다. 그래서 **강도를 낮춰 아낄 수 있는 것은 판정 몫뿐**이고,
그게 18%입니다.

### 🔶 경계선 장이 또 갈렸습니다

```
(10~12칸 답안지) 커트라인 -2
  Opus·high  오답 2 → PASS  (여유 0)
  Opus·low   오답 3 → FAIL
```

박준희와 다른 장인데 증상이 같습니다. **여유 0인 답안지는 무엇을 바꾸든
갈립니다.** 이제 두 번 확인됐습니다.

### ⚠️ 번호 없는 시험지에서는 정오 차이를 믿지 마십시오

17칸짜리 장의 정오 차이가 `+11`로 크게 나왔습니다. 이 답안지는
**번호가 인쇄돼 있지 않아 모델이 번호를 붙이는** 유형입니다(§13.8).

> 같은 "7번"이 **같은 칸이 아닐 수 있습니다.**

번호로 짝지어 비교하는 방식이 이 유형에서는 어긋납니다. 이 장은 마침
기준도 판정이 없어 통계에서 빠졌지만, **번호 없는 시험지가 표본에 많으면
정오 차이가 부풀려집니다.** 판정 일치만 보십시오.

### 결론과 남은 조건

**바꿔도 될 후보는 `Opus 5 + low` 하나입니다.** 다만 아직 근거가 얇습니다.

| 확인된 것 | 아직 아닌 것 |
|---|---|
| 6장에서 잡음과 구별 안 됨 | 표본이 **6장**뿐 |
| 읽기가 안 나빠짐 | 비교 가능한 4장이 **전부 PASS** |
| 비용 −18% · 시간 −26% | FAIL 답안지에서 안 재봄 |

**관대 편향은 PASS만 있는 표본에서 안 잡힙니다**(§13.14). 지금 판정이
잘 맞은 것도 그 한계 안의 이야기입니다.

→ 실사용으로 답안지가 쌓이면 **FAIL이 섞인 20~30장**으로 한 번 더 재고
그때 바꿉니다. 하루 300쪽 기준 월 22만 원 아끼는 결정이라, 몇 주 기다릴
값어치가 있습니다.
