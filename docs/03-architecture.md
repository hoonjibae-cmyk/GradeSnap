# 03. 시스템 아키텍처

> ⚠️ **이 문서의 일부는 [12. 페이지 단위 채점](12-page-level-grading.md)으로 대체되었습니다 (2026-08-07).**
>
> 기준 마커 정합 · QR 식별 · 템플릿 좌표 crop(§4의 단계 2~4)은 더 이상 쓰지 않습니다.
> 사진 한 장을 그대로 모델에 넣고 문항별로 전사받습니다.
> **규모 전제·기술 스택·실패 처리·보안(§1·§3·§5·§6)은 그대로 유효합니다.**

## 1. 규모 전제

먼저 규모를 못 박습니다. **학원 1~2곳, 교사 10명 내외, 하루 300장, 피크 동시 30장.**

이 규모에서는 마이크로서비스·Kafka·Kubernetes가 전부 과잉입니다.
**단일 웹앱 + 단일 워커 + Postgres**로 충분하며, 그 이상은 만들지 않습니다.

## 2. 구성

```
┌─────────────────────────────────────────────────┐

│   · 모바일: 촬영 / 업로드 / 진행상황            │
```

## 3. 기술 스택 결정

| 영역 | 선택 | 이유 |
|---|---|---|
| 프론트엔드 | **Next.js (App Router) + TypeScript + Tailwind** | 모바일 웹으로 앱 설치 없이 카메라 사용 가능. 템플릿 편집기 같은 밀도 높은 UI에 유리. |
| PDF 렌더 | **pdf.js** | 템플릿 편집기에서 PDF를 캔버스에 그리고 그 위에 영역 지정 |
| 백엔드 API | **Next.js Route Handlers** | 프론트와 한 저장소. 이 규모에서 별도 API 서버는 불필요. |
| 이미지 처리 워커 | **Python + OpenCV (FastAPI)** | 원근 보정·정합·마킹 판독은 Python 생태계가 압도적으로 편함. 이 부분만 분리. |
| DB / 스토리지 / 인증 | **Supabase (Postgres + Storage + Auth)** | 운영 인력이 없는 상황에서 인증·스토리지·RLS를 한 번에. Postgres이므로 나중에 자체 호스팅으로 이전 가능. |
| 작업 큐 | **Postgres `jobs` 테이블 + 워커 폴링** | 하루 300건에 Redis/Celery는 과잉. `FOR UPDATE SKIP LOCKED`로 충분. 나중에 필요하면 교체. |
| AI 채점 | **Claude API** | 문장형·서술형 채점 및 애매한 손글씨 판독. 근거를 함께 반환받아 검수 화면에 노출. |
| 손글씨 인식 | **하이브리드** (아래 참조) | |
| 배포 | 웹: Vercel / 워커: 단일 컨테이너(Fly.io·Cloud Run) | |

### 3.1 손글씨 인식 전략 — 핵심 결정

한국어 손글씨(단어 뜻)와 영어 손글씨(단어·문장)를 모두 읽어야 합니다.
**단일 OCR에 의존하지 않고, 문항 유형별로 경로를 나눕니다.**

| 대상 | 1차 경로 | 보조 |
|---|---|---|
| 선택형 마킹 (`유/반`) | OpenCV 픽셀 판정 (외부 API 미사용) | — |
| 짧은 한국어 뜻 | **VLM(Claude vision)에 정답 후보와 함께 crop 전달** | 상용 OCR |
| 영단어 빈칸 | 상용 OCR → 정규화 후 사전 매칭 | 실패 시 VLM |
| 영어 문장 | **VLM으로 판독 + 채점 동시 수행** | — |

**"정답 후보를 알려주고 읽게 한다"** 가 이 시스템의 핵심 아이디어입니다.
일반 OCR은 백지 상태에서 글자를 추정하지만, 우리는 그 칸에 올 수 있는 답을 이미 압니다.

```
[crop 이미지] + "이 칸의 정답은 '응답하다'이며,
                 '대답하다/반응하다'도 인정됩니다.
                 학생이 쓴 것이 이 중 하나입니까?
                 판독 불가하면 그렇게 답하세요."
```

이 방식은 인식 정확도를 크게 올리는 대신 **관대해질 위험**이 있습니다.
따라서 프롬프트에서 *"애매하면 무조건 판독 불가로 답하라"* 를 강하게 지시하고,
Phase 0에서 **일부러 오답을 쓴 샘플**로 관대함을 검증합니다.

> 상용 OCR은 한국어 손글씨 정확도를 실측한 뒤 선택합니다.
> Phase 0의 목적이 바로 이 벤치마크입니다. ([로드맵](07-roadmap.md) 참조)

## 4. 처리 파이프라인 상세

### 단계 1 — 전처리
- 문서 외곽 4점 검출 → 원근 변환(perspective transform)으로 정면화
- 조명 불균형 보정 (adaptive threshold / illumination normalization)
- 해상도 정규화: 템플릿 기준 **300 DPI 상당**으로 리샘플링
- 품질 점수 산출 (흐림 = Laplacian 분산, 잘림, 기울기)
  → 임계값 미달 시 **즉시 재촬영 요청**. 나쁜 이미지를 채점하는 것보다 낫습니다.

### 단계 2 — 식별
- QR 디코딩 → `template_id`, `page_no`, `version`
- QR 실패 시 선생님이 수동 선택 (드롭다운)
- 학생 식별: 촬영 세션에 반이 지정되어 있고, 이름란 crop을 함께 보여주며 선생님이 확정.
  학번 마킹 칸이 있으면 자동 판독.

### 단계 3 — 정합 (registration)
정확도를 좌우하는 가장 중요한 단계입니다.

- 페이지 네 모서리의 기준 마커(fiducial) 검출
- 마커 4점 ↔ 템플릿 기준 4점으로 **homography** 계산
- 이후 모든 좌표는 템플릿 좌표계(정규화된 페이지 공간)에서 다룸
- 마커를 3개 미만 찾으면 채점 중단 → 재촬영 요청
  (억지로 채점하면 crop이 어긋나 조용히 틀린 채점이 나옵니다. 최악의 실패 모드입니다.)

### 단계 4 — crop
- 템플릿의 `answer_region.bbox`로 잘라냄
- 안전 여백 2mm 추가 (글씨가 칸을 살짝 넘어간 경우 대비)
- 인쇄된 밑줄·괘선 제거(morphology)로 인식 방해 요소 감소
- crop 이미지는 **반드시 저장** — 검수 화면과 사후 분쟁 대응에 필요

### 단계 5 — 채점
→ [05. 채점 엔진](05-grading-engine.md)

### 단계 6 — 라우팅
- 문항별 확신도(0~1) 산출
- `≥ auto_confirm_threshold` → 자동 확정
- 그 미만 → 검수 큐
- 임계값은 템플릿별로 조정 가능

## 5. 실패 처리

| 실패 | 처리 |
|---|---|
| QR 미검출 | 수동 시험지 선택 |
| 기준 마커 3개 미만 | **채점 중단**, 재촬영 요청 |
| 품질 점수 미달 | 업로드 시점에 재촬영 요청 |
| 인식 API 오류 | 지수 백오프 재시도 3회 → 전 문항 검수 큐로 |
| AI 응답 스키마 불일치 | 재시도 1회 → 검수 큐로 |
| 채점 중 워커 크래시 | 잡 상태 `processing` 타임아웃 → 재큐잉 (멱등 처리) |

원칙: **불확실하면 자동 확정하지 않는다. 언제나 사람에게 넘긴다.**

## 6. 보안·개인정보

- 저장 데이터에 **학생 실명과 답안 이미지**가 포함됩니다.
- 스토리지 접근은 서명 URL만 허용, 만료 시간 짧게
- 교사는 담당 반 데이터만 조회 (Postgres RLS로 강제)
- 원본 이미지 보관 기간 정책 필요 (예: 학기 종료 후 N개월 뒤 자동 삭제)
- AI API로 전송되는 것은 **답안 영역 crop**이며, 이름란은 전송하지 않습니다.
- 학원 개인정보 처리방침에 자동채점 및 이미지 보관 사실 반영 필요
